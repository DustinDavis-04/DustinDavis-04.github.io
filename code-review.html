Code Review

Evaluating the Original Artifacts

Before beginning the capstone enhancements, I completed a detailed code review of each original artifact. The review helped me identify strengths, weaknesses, security concerns, design limitations, and opportunities for improvement before making changes to the projects.

Capstone Code Review

01

Software Engineering

Travlr Getaways

Review Findings

The original Travlr Getaways application had a strong full-stack foundation with separate public, API, database, and Angular administration areas. It already supported CRUD operations, MongoDB persistence, authentication, password hashing, and protected API routes.

The review also identified several areas for improvement. These included inconsistent API responses, limited server-side validation, duplicate trip codes, weaknesses in the login workflow, hard-coded configuration values, limited automated testing, and security concerns that needed to be addressed before the project could represent a more polished application.

Enhancement Direction

These findings guided the enhancement toward stronger validation, protected administrative access, improved error handling, better data integrity, and a more consistent administrative user experience.

02

Algorithms & Data Structures

Grazioso Salvare

Review Findings

The original Grazioso Salvare project already provided an interactive dashboard with rescue filters, a data table, breed graph, map, reset controls, CSV export, and reusable MongoDB CRUD operations.

The review showed that the original rescue logic was still based primarily on fixed pass-or-fail filtering. It also identified issues with the replacement Austin Animal Center datasets, hard-coded credentials, location assumptions, missing automated tests, unused starter code, and several callback and defensive-programming weaknesses.

Enhancement Direction

The review led to a new data-processing workflow that cleans the source data, matches intake and outcome records, calculates rescue suitability scores, ranks candidates, and handles missing location information more reliably.

03

Databases

Mobile Inventory App

Review Findings

The original Mobile Inventory App already supported account creation, login, inventory CRUD operations, quantity management, detailed item information, and low inventory alerts using a local SQLite database.

The review identified several important database and security limitations. Manufacturer and location information was repeated inside inventory records, passwords were stored in plain text, database upgrades destroyed existing data, deleted items were permanently removed, and there was no transaction history showing how inventory changed over time.

Enhancement Direction

These findings guided the database redesign toward normalization, foreign-key relationships, secure password storage, inventory history, soft deletion, improved location tracking, and a more realistic inventory-management workflow.
